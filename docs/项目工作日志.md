## 二、关键决策与理由

1. **增设 STG 清洗中间层**：把「枚举 → 异常/格式 → 合并映射」三步分别落 `stg_*_enum / stg_*_clean / stg_*_merge`，
   每步都能单独验证，答辩时可按步骤演示；四层架构本质不变，STG 只是 DWD 内部的加工过程。
2. **超大金额不删除、改为缩尾封顶**：直接删除会丢失订单关联的用户/门店/商品信息；
   封顶值取「正常区间 P95 = 4,745.32」并打标 `is_amount_capped`，可追溯也可还原。
3. **编码映射独立成维度表**：`gold → 金卡会员` 这类对照放进 `dim_*_code`，新增脏取值只需插一行，
   不必改清洗 SQL；DWD 层用 `LEFT JOIN` 完成转换，符合维度建模思路。
4. **品类分析走明细事实表 `dwd_order_item`**：订单事实表无 `product_id`，明细表才有；
   品类销售额用「单价 × 数量 × (1-折扣率)」口径，与订单支付金额不对齐，只比较占比。

## 三、踩坑记录

1. Hive 4 的 `CREATE TABLE` 默认是**外部表**，`DROP TABLE` 只删元数据 —— 脚本重跑会数据翻倍，
   甚至让 `stg_order_merge` 从 1.5 万膨胀到 12 万。已全面改为 `INSERT OVERWRITE` 幂等写入。
2. 动态分区 366 个超过默认上限（每节点 100），需放开 `hive.exec.max.dynamic.partitions.pernode`。
3. 单条 SQL 十几个 `UNION ALL` 会触发 Tez 计数器上限（120），需拆分为多条 `INSERT`。
4. 优惠金额必须在**支付金额封顶之后**再钳制，否则封顶后会出现 `discount > pay_amount` 的残留（实测 280 行）。

## 二、文档转 docx 的做法（工具链沉淀）

环境里没有 pandoc、python-docx 装不上（离线），改用**自带文档服务的 HTML→DOCX 通道**：

1. `tools/md2html.py`：Markdown → 带封面的 A4 排版 HTML。核心是两处 ASCII 图（四层架构、星型模型）
   改写成**表格化框图**（单元格底色 + 边框 + 箭头），避免等宽字符在 Word 里对不齐。
2. `convert_doc.py`（html-to-doc 技能）：HTML 一次性灌入空文档并另存为交付路径。
3. `tools/postprocess_docx.py`：补三处印刷细节 —— A4 纸张尺寸（转换器只写页边距不写纸张）、
   封面署名后插分页符（封面独立成页）、表格首行 `tblHeader` + 全行 `cantSplit`（长表跨页表头不丢）。

校验结果：三份文档标题 0 缺失、表格 8/19/17 张、关键数字（99.74%、3,847.05 万等）逐个比对一致；
`border="1"` 属性才会被映射成 Word 表格边框（只写 inline CSS 不生效，第一版就是边框全丢）。

## 三、过程中发现的两个真问题

1. **ARPU 差点算错 14.7 倍**：第一版 `ads_gmv_summary` 直接把 `dws_user_1d.buyer_cnt` 相加当作总用户数，

## 三、一个「不做」的决定

原计划做「浏览 → 加购 → 收藏 → 购买」行为转化漏斗，SQL 都写完了，跑出来才发现：

- 60,000 条行为只落在 58,132 个会话，**人均 1.03 条** —— 会话里根本串不成路径；
- 四类行为的去重用户数是 1000 / 1000 / 995 / 1000，**覆盖率≈100%**，第一层就没有筛选作用；
- 购买次数（11,969）**高于**加购（8,286），漏斗不可能越走越大。

这份埋点撑不起漏斗。硬做只能得出一组假转化率，答辩被追问「为什么加购比购买少」就崩了。
所以改成 `ads_behavior_coverage`：只报构成与覆盖，并在表里加 `funnel_valid = 0` 显式标注「不可作为漏斗环节」。
**能证明数据不能用，和能算出一个数，后者更容易，前者更值钱。**

## 四、RFM 与漏斗的关键数

- RFM：重要价值 164 人（16.4%）+ 重要保持 162 人（16.2%）= **32.6% 用户贡献 45.9% GMV**；
  一般挽留 356 人（35.6%）仍贡献 25.75% GMV，人均 1.85 万 → 召回主战场。
- 履约漏斗：15,000 → 9,966（66.44%）→ 5,642（37.61%）；
  支付前流失 **1,282.70 万**，支付后未履约再流失 **1,113.12 万**。

## 五、踩坑

1. `INSERT OVERWRITE TABLE ... WITH agg AS (...) SELECT` 在 Hive 4 直接报 `cannot recognize input near 'WITH'`。
   CTE 只能放在查询开头，不能跟在 INSERT 后面。改成三个分支内联聚合子查询（表才 1.5 万行，重复扫无所谓）。
2. `ALTER TABLE ... ADD COLUMNS` 加的新列只能追加在最后一个普通字段之后、分区字段之前 ——
   正好符合需求，但如果想插在中间就必须重建表。
