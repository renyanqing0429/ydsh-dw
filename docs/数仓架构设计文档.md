# 云购生活新零售企业数仓 —— 数据仓库架构设计文档（第 2 周）

> 项目：企业级数据仓库与经营分析可视化系统
> 阶段：第 2 周（数据清洗进阶 · Hive 四层数仓建模 · 探索性分析）
> 范围：ODS → DWD 分层落地，DWS / ADS 为后续周的规划占位

---

## 一、设计目标

1. **可追溯**：每一层数据都能回溯到上一层，清洗动作留有标记字段（如 `is_amount_capped`、`is_email_missing`）。
2. **可复用**：清洗逻辑沉淀在 DWD 层，上层（DWS / ADS）只做汇总与指标计算，不重复清洗。
3. **高性能**：事实表按日期分区 + ORC 列式存储，热表辅以分桶，避免全表扫描。
4. **规范统一**：库 / 表 / 字段命名有明确前缀与语义，杜绝同名不同义。

## 二、四层架构总览

```
                        数据源（业务系统 / CSV 模拟数据）
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ODS 贴源层  ydsh_ods.ods_*                                   │
│ 定位：原样接入，不做任何业务加工，保留原始脏数据证据           │
│ 粒度：最细粒度；存储：TEXTFILE；生命周期：全量快照             │
└─────────────────────────────────────────────────────────────┘
                                     │  清洗：缺失值填充 / 去重 / 枚举标准化
                                     │        异常值修正 / 格式统一 / 字段拆分合并
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│ STG 清洗中间层  ydsh_dwd.stg_*  （本项目为便于复盘而增设）     │
│ 定位：承接 ODS → DWD 的清洗过程，分步骤落中间结果，可逐步验证   │
│ 粒度：同 ODS；存储：默认格式；可随时重跑                       │
└─────────────────────────────────────────────────────────────┘
                                     │  建模：星型模型，维度退化与编码映射
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│ DWD 明细层  ydsh_dwd.dwd_* / dim_*                            │
│ 定位：清洗 + 标准化 + 维度关联后的明细数据，全仓库唯一事实来源   │
│ 粒度：事务粒度（订单 / 明细 / 行为）；存储：ORC；分区：按日期    │
└─────────────────────────────────────────────────────────────┘
                                     │  汇总：按主题域轻度聚合（日 / 周 / 月 + 维度）
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│ DWS 汇总层  ydsh_dws.dws_*   （第 3 周落地）                  │
│ 定位：面向分析主题的宽表，一次加工多次复用，降低 ADS 计算成本    │
│ 粒度：日 / 周 / 月 + 维度组合；存储：ORC + 分区                 │
└─────────────────────────────────────────────────────────────┘
                                     │  应用：指标口径固化、报表直读
                                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ADS 应用层  ydsh_ads.ads_*   （第 4 周落地）                   │
│ 定位：面向报表与可视化的结果表，一行即一个指标                  │
│ 粒度：指标级；存储：ORC（小结果集可导 MySQL 供 BI 直连）        │
└─────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
                        经营分析看板（可视化 / 报表 / 大屏）
```

### 分层职责对照表

| 分层 | 定位 | 库名 | 表名前缀 | 数据粒度 | 存储 | 是否对外 |
|---|---|---|---|---|---|---|
| ODS 贴源层 | 原样接入业务数据，保留原始形态 | `ydsh_ods` | `ods_` | 最细粒度（原始行） | TEXTFILE | 否 |
| STG 中间层 | 分步骤清洗的过程结果，便于复盘与重跑 | `ydsh_dwd` | `stg_` | 同 ODS | 默认 | 否 |
| DWD 明细层 | 清洗、标准化、维度关联后的明细数据 | `ydsh_dwd` | `dwd_` / `dim_` | 事务粒度 | ORC + 分区 | 是（分析基线） |
| DWS 汇总层 | 面向主题的轻度汇总宽表 | `ydsh_dws` | `dws_` | 日/周/月 + 维度 | ORC + 分区 | 是 |
| ADS 应用层 | 面向报表与指标的最终结果 | `ydsh_ads` | `ads_` | 指标级 | ORC / MySQL | 是（BI 直读） |

> 说明：STG 层是本项目为「清洗过程可逐步验证、可答辩演示」增设的中间层，不改变四层架构的本质；若追求极简，可在规模化后合并回 DWD 的临时表。

## 三、DWD 层星型模型（本期落地）

```
                      ┌──────────────┐
                      │   dim_date   │  时间维度（2024 全年 366 天）
                      └──────┬───────┘
                             │ date_id
   ┌──────────────┐          │          ┌────────────────┐
   │   dim_user   │────user_id──────────▶                │
   └──────────────┘          │          │   dwd_order    │  订单事实表（订单粒度）
                             │          │  分区 order_date│
   ┌──────────────┐          │          │                │
   │  dim_store   │────store_id────────▶└───────┬────────┘
   └──────────────┘                             │ order_id
                                                ▼
                                     ┌────────────────────┐
   ┌──────────────┐                  │  dwd_order_item    │  明细事实表（商品粒度）
   │ dim_product  │────product_id───▶│  分区 order_date    │
   └──────────────┘                  └────────────────────┘

   ┌──────────────┐    user_id     ┌──────────────────────────┐
   │   dim_user   │───────────────▶│  dwd_user_behavior       │  行为事实表（行为粒度）
   └──────────────┘                │  分区 behavior_date      │
   ┌──────────────┐  product_id    │  + 分桶版本（8 桶）       │
   │ dim_product  │───────────────▶└──────────────────────────┘
   └──────────────┘
```

### 事实表（度量在哪儿）

| 表名 | 粒度 | 度量字段 | 外键 | 分区 / 分桶 |
|---|---|---|---|---|
| `dwd_order` | 一个订单一行 | `pay_amount`、`discount_amount` | `user_id`、`store_id`、`order_date` | 分区 `order_date`（366 个） |
| `dwd_order_item` | 一个订单商品一行 | `quantity`、`unit_price`、`item_amount` | `order_id`、`user_id`、`product_id`、`order_date` | 分区 `order_date` |
| `dwd_user_behavior` | 一次行为一行 | 行为计数、`is_conversion` | `user_id`、`product_id`、`behavior_date` | 分区 `behavior_date`；另建分桶版本 `dwd_user_behavior_bucket`（按 `user_id` 分 8 桶） |

### 维度表（描述属性在哪儿）

| 表名 | 主键 | 主要属性 | 行数 |
|---|---|---|---|
| `dim_user` | `user_id` | 性别、年龄、年龄段、省份、城市、地域、注册日期、会员等级、等级权重、手机、邮箱 | 1,000 |
| `dim_product` | `product_id` | 类目、子类目、品牌、售价、价格带、成本、库存、状态、上架日期 | 600 |
| `dim_store` | `store_id` | 门店名、省市区、地址、开业日期、面积、店长 | 60 |
| `dim_date` | `date_id` | 年、季度、月、年月、日、周几、是否周末 | 366 |

### 编码映射维度表（本期新增，用于「编码 → 规范中文名」转换）

| 表名 | 作用 | 示例 |
|---|---|---|
| `dim_member_level_code` | 会员等级编码映射（含等级权重） | `gold` → 金卡会员（权重 3） |
| `dim_pay_type_code` | 支付方式编码映射 | `wechat` / `微信` → 微信支付 |
| `dim_order_status_code` | 订单状态编码映射（含是否有效订单标记） | `cancelled` / `3` → 已取消（有效=0） |
| `dim_channel_code` | 渠道编码映射 | `app` → APP、`pc` → PC官网 |
| `dim_behavior_type_code` | 行为类型编码映射（含是否转化行为） | `cart` → 加购、`buy` → 购买（转化=1） |

> 设计要点：**度量字段进事实表，描述属性进维度表**；编码对照独立成表后，新增一种脏取值只需 INSERT 一行映射，无需改动清洗 SQL，符合开闭原则。

## 四、分区与分桶策略

| 策略 | 选型 | 理由 |
|---|---|---|
| 分区字段 | 订单用 `order_date`（天）、行为用 `behavior_date`（天） | 业务查询 90% 带时间范围（日报 / 周报 / 月报），按天分区可精确裁剪；一年 366 个分区，数量可控，不会小文件爆炸 |
| 分区粒度 | 天（而非月） | 数据量 1.5 万单 / 6 万行为，天级分区单分区约 41 单，配合 ORC 仍可接受；若数据量上亿则需改为月分区或天分区 + 合并小文件 |
| 分桶 | `dwd_user_behavior_bucket` 按 `user_id` 分 8 桶，桶内按 `behavior_time` 排序 | 用户级聚合（如单用户漏斗）可桶裁剪；分桶后 JOIN 可走 bucket map join |
| 存储格式 | 全部 `STORED AS ORC` | 列式存储 + 压缩，减少 IO；支持谓词下推 |

分区裁剪示例（查询只扫 90 个分区而非全表 366 个）：

```sql
SELECT COUNT(*) FROM ydsh_dwd.dwd_order
WHERE order_date >= '2024-01-01' AND order_date <= '2024-03-31';
```

## 五、命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 数据库 | `ydsh_<分层>` | `ydsh_ods`、`ydsh_dwd`、`ydsh_dws`、`ydsh_ads` |
| ODS 表 | `ods_<业务实体>` | `ods_order`、`ods_user_behavior` |
| DWD 事实表 | `dwd_<业务过程>` | `dwd_order`、`dwd_order_item` |
| DWD 维度表 | `dim_<维度名>` | `dim_user`、`dim_date` |
| 编码映射表 | `dim_<维度名>_code` | `dim_pay_type_code` |
| 中间层表 | `stg_<实体>_<步骤>` | `stg_order_enum`、`stg_order_clean`、`stg_order_merge` |
| 临时/辅助表 | `tmp_<用途>` | `tmp_amount_cap`、`tmp_age_mean` |
| 分区字段 | 与业务日期同名 | `order_date`、`behavior_date` |
| 标记字段 | `is_<含义>`（INT，1/0） | `is_valid_order`、`is_amount_fixed` |
| 金额字段 | 统一 DOUBLE，保留 2 位 | `pay_amount`、`item_amount` |
| 脚本目录 | `sql/<分层或环节>/<动作>.sql` | `sql/dwd/load_dwd.sql` |

## 六、ETL 流程与脚本清单

| 步骤 | 脚本 | 输入 | 输出 |
|---|---|---|---|
| ① 建库建表 | `sql/ods/create_ods.sql` | CSV 数据字典 | `ydsh_ods.ods_*` |
| ② 数据加载 | `sql/ods/load_ods.sql` | `data/*.csv` | ODS 各表 |

| ④ 缺失值 / 去重（第 1 周） | `sql/clean/missing_values.sql`、`sql/clean/dedup.sql` | ODS | `ydsh_ods.dwd_user / dwd_product / dwd_order` |
| ⑤ 枚举标准化（第 2 周） | `sql/clean/standardize_enum.sql` | ODS | `ydsh_dwd.stg_*_enum` |
| ⑥ 异常值与格式（第 2 周） | `sql/clean/outlier_format.sql` | `stg_*_enum` | `ydsh_dwd.stg_*_clean` |
| ⑦ 字段合并 + 编码映射（第 2 周） | `sql/clean/split_merge.sql` | `stg_*_clean` | `stg_*_merge`、`dim_*_code` |
| ⑧ DWD 建模 | `sql/dwd/create_dwd.sql` | — | `dim_*`、`dwd_*`（ORC + 分区） |
| ⑨ DWD 加载 | `sql/dwd/load_dwd.sql` | `stg_*_merge` | DWD 各表 + 分桶表 |
| ⑩ 质量对比 | `sql/quality/quality_compare.sql` | ODS vs DWD | 五类脏数据修复率 |
| ⑪ 探索性分析 | `sql/analysis/exploratory_analysis.sql` | DWD | KPI 与多维分布 |
