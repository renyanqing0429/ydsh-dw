# 云购生活新零售企业数仓 —— 数据仓库架构设计文档（第 2 周）

> 项目：企业级数据仓库与经营分析可视化系统
> 阶段：第 2 周（数据清洗进阶 · Hive 四层数仓建模 · 探索性分析）
> 范围：ODS → DWD → DWS → ADS 四层全部落地（DWS 4 张日汇总表、ADS 13 张应用表，均已在 Hive 实测）

---

## 一、设计目标

1. **可追溯**：每一层数据都能回溯到上一层，清洗动作留有标记字段（如 `is_amount_capped`、`is_email_missing`）。
2. **可复用**：清洗逻辑沉淀在 DWD 层，上层（DWS / ADS）只做汇总与指标计算，不重复清洗。
3. **高性能**：事实表按日期分区 + ORC 列式存储，热表辅以分桶，避免全表扫描。
4. **规范统一**：库 / 表 / 字段命名有明确前缀与语义，杜绝同名不同义。

### 事实表（度量在哪儿）

| 表名 | 粒度 | 度量字段 | 外键 | 分区 / 分桶 |
|---|---|---|---|---|
| `dwd_order` | 一个订单一行 | `pay_amount`（原始）、`discount_amount`（原始）、**`pay_amount_valid` / `discount_amount_valid`（有效金额，主口径）** | `user_id`、`store_id`、`order_date` | 分区 `order_date`（366 个） |
| `dwd_order_item` | 一个订单商品一行 | `quantity`、`unit_price`、`item_amount` | `order_id`、`user_id`、`product_id`、`order_date` | 分区 `order_date` |
| `dwd_user_behavior` | 一次行为一行 | 行为计数、`is_conversion` | `user_id`、`product_id`、`behavior_date` | 分区 `behavior_date`；另建分桶版本 `dwd_user_behavior_bucket`（按 `user_id` 分 8 桶） |

| 表名 | 作用 | 示例 |
|---|---|---|
| `dim_member_level_code` | 会员等级编码映射（含等级权重） | `gold` → 金卡会员（权重 3） |

## 四、DWS 汇总层（本期落地）

DWS 是本轮新增的**中间汇总层**：把「按主题域、按天的轻度聚合」固化成表，ADS 只做取数与排名，不再重复扫明细。
四张表全部按 `dt` 分区、ORC 存储、`INSERT OVERWRITE` 写入，可反复重跑。

| 表名 | 粒度 | 上游 | 实测行数 | 分区数 |
|---|---|---|---|---|
| `dws_order_1d` | 统计日 | `dwd_order` | 366 | 366 |
| `dws_user_1d` | 统计日 | `dwd_order` + `dim_user` | 366 | 366 |
| `dws_category_1d` | 统计日 × 一级类目 | `dwd_order_item` + `dim_product` | 2,928 | 366 |
| `dws_channel_1d` | 统计日 × 渠道 | `dwd_order` | 1,464 | 366 |

合计 5,124 行。脚本：`sql/dws/create_dws_load.sql`；实测输出：`docs/执行结果/13_DWS层构建结果.txt`。

### 三个设计要点

1. **只聚合、不清洗**：脏数据在 DWD 已处理完，DWS 里出现任何 `NULL` 或异常值都应当回头查 DWD，而不是在这里补救。
2. **维度退化**：把 `category`、`channel` 这类高频过滤字段直接冗余进汇总表，避免 ADS 再 JOIN 维度表。
3. **ARPU 不能用日汇总相加**：`dws_user_1d.buyer_cnt` 按日相加得到 **14,675**，而真实下单用户只有 **1,000** 人——
同一用户跨天被重复计数 14.7 倍。所以 `ads_gmv_summary` 的 ARPU 单独从 DWD 全周期去重后取数，这是汇总层最容易踩的坑。

### 后 6 张表为什么这么设计

1. **RFM 补充的是「维度」，不是「排名」**：`ads_user_value_seg` 只按累计金额切三段，回答「谁花得多」；
   RFM 引入 R（最近消费间隔）与 F（频次），才能回答「谁快流失、谁值得追第二单」。
   打分用 `NTILE(5)` 五分位，避免拍阈值；8 类客群按「高/低」二分组合，标签与运营话术一一对应。
2. **行为漏斗被主动否决**：原本计划用 `dwd_user_behavior` 做浏览→加购→收藏→购买漏斗，
   实测 60,000 条行为只落在 58,132 个会话（1.03 条/会话），四类行为 UV 为 1000/1000/995/1000，
   购买次数（11,969）反超加购（8,286），**不满足漏斗必须单调递减的前提**。
   因此没有输出转化率，而是建 `ads_behavior_coverage` 并置 `funnel_valid = 0`，把「数据不可用」本身作为结论交付。
3. **履约漏斗改用订单状态**：订单状态天然单调（提交 ⊇ 支付成功 ⊇ 已完成），且每笔无效订单都写了金额，
   `原始金额 − 有效金额` 直接等于该步流失金额，一步就能量化「钱漏在哪」。
4. **口径下沉到事实表**：`dwd_order` 新增 `pay_amount_valid` / `discount_amount_valid`，
   无效订单在本层置 0；DWS/ADS 直接 `SUM(pay_amount_valid)`，不再层层重复写
   `SUM(CASE WHEN is_valid_order = 1 ...)` —— 少一次手写条件，就少一处口径漂移的机会。
5. **单品榜要带帕累托分层**：只给一张按销售额排序的 600 行清单，看的人无从判断「够不够集中」。
   于是用累计占比把 SKU 切成 A 头部（累计 ≤80%）/ B 中部（80~95%）/ C 长尾（>95%），
   一眼看出「408 个 SKU 才凑出 80% 销售」，比列 600 行数字有用。
6. **坪效必须真 JOIN 门店面积**：`dwd_order_item` 本身不带订单状态，做商品榜时要回 JOIN `dwd_order`
   才能过滤无效单；门店 GMV 用 `LEFT JOIN` 接 `dim_store`，保证 0 单门店也留在结果里
   （否则「低效门店」会被人为筛掉，正好漏掉最该看的对象）。

### 口径对照：为什么 GMV 有两个数

源数据里**取消 / 退款 / 待支付订单同样填了 `pay_amount`**（5,034 笔，合计 1,282.70 万），
若直接 `SUM(pay_amount)` 会把没成交的钱算进 GMV。因此 ADS 确立主口径为「有效订单」，全订单口径只作对照列保留：

| 指标 | 有效订单口径（ADS 主口径） | 全订单口径（探索性分析简报） | 差异原因 |
|---|---|---|---|
| GMV | 25,643,462.77 | 38,470,434.95 | 无效订单金额被计入 |
| 客单价 | 2,573.09 | 2,564.70 | 分子分母同步变化，差异小 |
| 用户分层阈值 | 3.5 万 / 2 万（按有效口径 P80 / P40 重标定） | 5 万 / 2 万 | 人均消费 2.56 万 vs 3.85 万 |

> **已实施（v1.2，2026-11-03）**：口径下沉到 DWD —— `dwd_order` 新增 `pay_amount_valid` / `discount_amount_valid`，
> 加载时对无效订单置 0，原始 `pay_amount` 保留（供「全订单口径」对照与流失金额计算）。
> DWS 四张表全部改读有效金额字段，ADS 主口径随之统一；四层对账仍为 0 差异，说明改造未改变任何已交付数字。
> 保留原始字段而不是直接改写 `pay_amount`，是为了让「流失了多少钱」可以用减法算出来 —— 这正好是履约漏斗的数据基础。

## 六、分区与分桶策略

| 策略 | 选型 | 理由 |
|---|---|---|
| 分区字段 | 订单用 `order_date`（天）、行为用 `behavior_date`（天） | 业务查询 90% 带时间范围（日报 / 周报 / 月报），按天分区可精确裁剪；一年 366 个分区，数量可控，不会小文件爆炸 |
| 分区粒度 | 天（而非月） | 数据量 1.5 万单 / 6 万行为，天级分区单分区约 41 单，配合 ORC 仍可接受；若数据量上亿则需改为月分区或天分区 + 合并小文件 |
| 分桶 | `dwd_user_behavior_bucket` 按 `user_id` 分 8 桶，桶内按 `behavior_time` 排序 | 用户级聚合（如单用户漏斗）可桶裁剪；分桶后 JOIN 可走 bucket map join |
| 存储格式 | 全部 `STORED AS ORC` | 列式存储 + 压缩，减少 IO；支持谓词下推 |

分区裁剪示例（查询只扫 90 个分区而非全表 366 个）：

```sql
SELECT COUNT(*) FROM ydsh_dwd.dwd_order
WHERE order_date >= '2024-01-01' AND order_date <= '2024-03-31';
```

| 中间层表 | `stg_<实体>_<步骤>` | `stg_order_enum`、`stg_order_clean`、`stg_order_merge` |
| 临时/辅助表 | `tmp_<用途>` | `tmp_amount_cap`、`tmp_age_mean` |
| 分区字段 | 与业务日期同名 | `order_date`、`behavior_date` |
| 标记字段 | `is_<含义>`（INT，1/0） | `is_valid_order`、`is_amount_fixed` |
| 金额字段 | 统一 DOUBLE，保留 2 位 | `pay_amount`、`item_amount` |
| 脚本目录 | `sql/<分层或环节>/<动作>.sql` | `sql/dwd/load_dwd.sql` |
