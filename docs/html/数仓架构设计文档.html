云购数仓组

一、设计目标

  1. 可追溯：每一层数据都能回溯到上一层，清洗动作留有标记字段（如 is_amount_capped、is_email_missing）。
  2. 可复用：清洗逻辑沉淀在 DWD 层，上层（DWS / ADS）只做汇总与指标计算，不重复清洗。
  3. 高性能：事实表按日期分区 + ORC 列式存储，热表辅以分桶，避免全表扫描。
  4. 规范统一：库 / 表 / 字段命名有明确前缀与语义，杜绝同名不同义。

四、DWS 汇总层（本期落地）

DWS 是本轮新增的中间汇总层：把「按主题域、按天的轻度聚合」固化成表，ADS 只做取数与排名，不再重复扫明细。 四张表全部按 dt 分区、ORC 存储、INSERT OVERWRITE 写入，可反复重跑。

表名粒度上游实测行数分区数
dws_order_1d统计日dwd_order366366
dws_user_1d统计日dwd_order + dim_user366366
dws_category_1d统计日 × 一级类目dwd_order_item + dim_product2,928366
dws_channel_1d统计日 × 渠道dwd_order1,464366

合计 5,124 行。脚本：sql/dws/create_dws_load.sql；实测输出：docs/执行结果/13_DWS层构建结果.txt。

三个设计要点

  1. 只聚合、不清洗：脏数据在 DWD 已处理完，DWS 里出现任何 NULL 或异常值都应当回头查 DWD，而不是在这里补救。
  2. 维度退化：把 category、channel 这类高频过滤字段直接冗余进汇总表，避免 ADS 再 JOIN 维度表。
  3. ARPU 不能用日汇总相加：dws_user_1d.buyer_cnt 按日相加得到 14,675，而真实下单用户只有 1,000 人——

同一用户跨天被重复计数 14.7 倍。所以 ads_gmv_summary 的 ARPU 单独从 DWD 全周期去重后取数，这是汇总层最容易踩的坑。

后 4 张表为什么这么设计

  1. RFM 补充的是「维度」，不是「排名」：ads_user_value_seg 只按累计金额切三段，回答「谁花得多」；

RFM 引入 R（最近消费间隔）与 F（频次），才能回答「谁快流失、谁值得追第二单」。 打分用 NTILE(5) 五分位，避免拍阈值；8 类客群按「高/低」二分组合，标签与运营话术一一对应。

  1. 行为漏斗被主动否决：原本计划用 dwd_user_behavior 做浏览→加购→收藏→购买漏斗，

实测 60,000 条行为只落在 58,132 个会话（1.03 条/会话），四类行为 UV 为 1000/1000/995/1000， 购买次数（11,969）反超加购（8,286），不满足漏斗必须单调递减的前提。 因此没有输出转化率，而是建 ads_behavior_coverage 并置 funnel_valid = 0，把「数据不可用」本身作为结论交付。

  1. 履约漏斗改用订单状态：订单状态天然单调（提交 ⊇ 支付成功 ⊇ 已完成），且每笔无效订单都写了金额，

原始金额 − 有效金额 直接等于该步流失金额，一步就能量化「钱漏在哪」。

  1. 口径下沉到事实表：dwd_order 新增 pay_amount_valid / discount_amount_valid，

无效订单在本层置 0；DWS/ADS 直接 SUM(pay_amount_valid)，不再层层重复写 SUM(CASE WHEN is_valid_order = 1 ...) —— 少一次手写条件，就少一处口径漂移的机会。

口径对照：为什么 GMV 有两个数

源数据里取消 / 退款 / 待支付订单同样填了 pay_amount（5,034 笔，合计 1,282.70 万）， 若直接 SUM(pay_amount) 会把没成交的钱算进 GMV。因此 ADS 确立主口径为「有效订单」，全订单口径只作对照列保留：

保留原始字段而不是直接改写 pay_amount，是为了让「流失了多少钱」可以用减法算出来 —— 这正好是履约漏斗的数据基础。

六、分区与分桶策略

策略选型理由
分区字段订单用 order_date（天）、行为用 behavior_date（天）业务查询 90% 带时间范围（日报 / 周报 / 月报），按天分区可精确裁剪；一年 366 个分区，数量可控，不会小文件爆炸
分区粒度天（而非月）数据量 1.5 万单 / 6 万行为，天级分区单分区约 41 单，配合 ORC 仍可接受；若数据量上亿则需改为月分区或天分区 + 合并小文件
分桶dwd_user_behavior_bucket 按 user_id 分 8 桶，桶内按 behavior_time 排序用户级聚合（如单用户漏斗）可桶裁剪；分桶后 JOIN 可走 bucket map join
存储格式全部 STORED AS ORC列式存储 + 压缩，减少 IO；支持谓词下推

分区裁剪示例（查询只扫 90 个分区而非全表 366 个）：

SELECT COUNT(*) FROM ydsh_dwd.dwd_order
WHERE order_date >= '2024-01-01' AND order_date <= '2024-03-31';
